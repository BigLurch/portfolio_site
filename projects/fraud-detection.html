The project

I built a production-style fraud detection platform to explore what happens around an ML service after deployment. Synthetic transactions are scored through an API, stored as prediction logs and presented in a dashboard.

What I built

  • Synthetic transaction generation, feature engineering and a Random Forest classifier.
  • FastAPI inference with fraud probability and low, medium or high risk labels.
  • Prediction logging to PostgreSQL when DATABASE_URL is configured, or JSONL when it is absent.
  • A Streamlit dashboard with transaction feeds, risk indicators and simulated map locations.
  • Separate API, dashboard and simulator services in Docker Compose.
  • MLflow tracking, Evidently drift reports and CI that generates data and trains the model before running pytest.

System at a glance

A simplified view of the main components and their roles.

  1. Transaction simulatorSend synthetic payment requests
  2. FastAPI + modelTransform features and score risk
  3. Prediction logsPostgreSQL when configured; otherwise JSONL
  4. Streamlit dashboardRead logs and inspect transactions
  5. Drift analysisCompare reference and current data with Evidently
  6. Development checksGenerate data, train and test in CI

Engineering decisions

Connect independent services

Docker Compose gives the API, dashboard and simulator separate roles. The dashboard and simulator use API_URL to reach the inference service.

Store predictions across environments

The logger selects PostgreSQL when a database URL is configured and JSONL otherwise. This supports different environments, but is not automatic failover if the database becomes unavailable.

Inspect changing data

Evidently reporting provides a way to compare new data against reference data. These drift reports complement the prediction dashboard.

Scope & limitations

Training data, transaction traffic and map coordinates are synthetic. The dashboard demonstrates system behavior, rather than real payment activity. This is a portfolio system, with no claim of bank-ready accuracy, production security or full observability.

Where I'd take it next

Real-data evaluation, explicit alerting, robust database error handling and clearer model promotion policies would be useful next steps.
